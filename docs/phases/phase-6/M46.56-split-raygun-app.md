# M46.56: Split raygun-app into crates

Status: in progress: step 1 and the first leaves of step 2 are done (see Measure).

## Why

`raygun-app` is one crate of about 158,000 lines (222 files). rustc's front end (parsing, macro
expansion, type checking, borrow checking) runs one crate on one thread, so however many cores a
machine has, this crate builds alone at the end of every build:

- A release build on a 4-core GitHub runner spends about 25 of its 50 minutes after the last
  dependency compiles: that is `raygun-app` (front end, codegen, thin-LTO link). Its dependencies
  are cached since v1.9.7 (a weekly build on main keeps the Rust caches warm); this part is not.
- Every local `cargo check`, clippy and test run after a change anywhere in the app rebuilds all of
  it, and parallel worktree agents each rebuild it.

Split into crates of about 5,000 to 15,000 lines, the front ends run side by side, and a change
rebuilds only its crate and those above it.

What everything leans on:

- `startup` is referenced by 60 modules, almost always for `startup::AppDb` (76 uses) and
  `startup::AppPaths` (12): handles that belong in a shared base, not in the start-up code.
- `events` (48 modules), `settings` (39), `device_state` (16), `privacy` (16), `local_network`
  (12): small and depending on nothing else in the crate. The natural base.
- Services find each other through Tauri's state (`app.state::<T>()`, 415 lookups; `try_state` 101).
  New crates can keep doing that (they depend on `tauri`), so the split is about which crate owns a
  type, not about rewriting the wiring. Only cycles have to be broken.
- `commands.rs` holds 502 of the commands; a few modules call into it (`pick_backup_folder`,
  `pick_local_folder`, `request_media_access`), which turns around once those move to the base.

The full module-to-module list (who uses whom) is regenerated with
`python ../../../tools/app_module_deps.py` run from `crates/raygun-app/src` (it writes
`app-deps.txt` there; don't commit that).

## The shape

```
raygun-app-base      events, settings service, AppDb/AppPaths, device_state, privacy,
                     local_network, network_mode, notifications model, the app's error type,
                     small helpers (picker, permissions requests). No domain logic.
   │
   ├─ raygun-app-sources    extensions, catalog, source_detect/source_queue, extension_installs,
   │                        servers, browser_check, web_views, genres, search_filter
   ├─ raygun-app-music      playback, resolver/resolution, collections, library, lyrics_store,
   │                        sound, details, durations, discovery, cover_fallback/cover_search,
   │                        quick_access, made_for_you, import, follows
   ├─ raygun-app-downloads  music_downloads, manga_downloads, video_downloads, website_downloads
   ├─ raygun-app-export     export/ (its pure parts first: remux, convert, names)
   ├─ raygun-app-video      video, video_session*, video_quality, video_links, video_sources,
   │                        video_library, video_subtitles, torrents, aniskip, sponsorblock, stremio
   ├─ raygun-app-reading    manga, novel, epub, comics, library_actions, dictionary, reader_ai,
   │                        text_translation, tts
   ├─ raygun-app-podcasts   podcasts, podcast_feed, captions
   ├─ raygun-app-answers    answers/
   └─ raygun-app-net        cast, connect, device_sync, device_link, remote, web_remote, websites,
                            mcp
raygun-app           startup (wiring), lib.rs (the builder: collect_commands!/collect_events!),
                     the remaining commands, backup (it reaches into everything), crash_log,
                     updates, app_window, open_with
```

The groups are a starting point: the dependency list decides. Two crates that need each other's
types either merge, or the shared types move down into the base (or a small `*-types` module of
the lower one), or one side talks to the other through a trait object or an event set in the base.

## Rules

- Each crate owns its services and its commands (`#[tauri::command]` functions next to the service
  they call, not in one `commands.rs`). `raygun-app`'s builder lists them by path in
  `tauri_specta::collect_commands!` and `collect_events!`; the bindings must come out the same
  (the bindings test checks).
- No crate depends on one above it. A service that needs something from a higher crate gets it as a
  trait object registered at start-up (in `startup.rs`), never by naming the higher crate.
- Tests move with their code. `raygun-app`'s test count stays the same across the move.
- One crate per step, each step a commit that builds, passes the full check and runs on the
  emulator: the app works between every step.
- Nothing changes behaviour. A move commit contains moves and the visibility (`pub(crate)` →
  `pub`) and path (`crate::` → `raygun_app_x::`) edits they need, nothing else.

## Order

1. **Base.** Create `raygun-app-base`; move `events`, `AppDb`/`AppPaths` (out of `startup`),
   `settings` (the service and `apply_live`'s hooks), `device_state`, `privacy`, `local_network`,
   `network_mode`, the notifications model. Re-export from `raygun-app` at first
   (`pub use raygun_app_base::events;`) so the rest keeps compiling unchanged; remove the
   re-exports once each moved crate names the base directly.
2. **Leaves first**, each one step: `answers` (used only by backup), `export`'s pure parts
   (remux/convert do no app calls), `dictionary`, `cast`, `websites`, `podcasts` + `captions`.
3. **The middle**: `sources` (extensions, catalog: many depend on it), then `music`, `reading`,
   `video`, `downloads`.
4. **Commands**: by now most commands have moved with their services; what's left in
   `commands.rs` is the app's own.
5. **Measure** after each step and at the end: `cargo build --release --timings` (and the debug
   build's) on a 4-core setting (`-j 4`) to match GitHub's runners; record the before and after in
   this file. Target: no single crate over ~20,000 lines, a release build of the app's own crates
   under 10 minutes on 4 cores.
6. **CI**: with the app in many crates, `Swatinem/rust-cache`'s `cache-workspace-crates: true` lets
   a release reuse unchanged app crates from the weekly build, not only the dependencies. Decide
   once the sizes are known (the cache budget is 10 GB a repository).

## Risks

- **Cycles hide in `app.state::<T>()` lookups**: they don't show as `crate::` paths. Grep for each
  moved service type's name before moving it.
- **`specta`/`tauri-specta` across crates**: types used by commands must derive `specta::Type`
  wherever they live (they already do in `raygun-model`); events defined in the base must still be
  collected by name in `lib.rs`.
- **Android**: the JNI entry points (`android.rs` and the `Java_…` exports) must stay in the crate
  that becomes the `.so` (`raygun-app`/`raygun_lib`), calling into the others.
- **Feature flags and `cfg`s** (`windows`, `android`, `desktop`) must be repeated in each crate's
  `Cargo.toml` that needs them; CI's Linux clippy catches the misses.
- **Merge pain with parallel work**: moving files conflicts with everything. Do the split when no
  other agent works in `raygun-app`, a few crates a day, and merge right after each.

## Checks

The full lead check after every step, the emulator after every step that moves a service with an
Android side (playback, video, downloads, captions), and a desktop start before the last step.

## Measure

`cargo build --release -p raygun-app --timings -j 4` on Windows (the development PC limited to 4
jobs), dependencies already built; times in seconds from the timing report.

|---|---|---|
| `raygun-app` lines | 158,360 | 127,552 |

The app's own crates went from 151 s to 130 s of wall time. The thin-LTO link of the final binary
(about 5 minutes on 4 jobs) is now the largest part, and splitting doesn't shorten it; a CI release
spends it once per target.
